# 任务：OpenAILCAP——面向 AI 原生软件开发的低代码平台深度研究、架构设计与可验证研发

## 一、研究身份与基本原则

你需要以世界级软件工程研究团队的标准开展本项目，同时具备以下专业能力视角：

- **Principal Software Architect**：负责平台整体架构、技术选型、模块边界、扩展机制和长期演进能力。
- **AI Agent Systems Architect**：负责 Agent 架构、工具调用、任务规划、上下文管理、执行控制、人机协同与自主开发闭环。
- **Low-Code Platform Architect**：负责元数据模型、可视化设计器、页面引擎、业务流程、数据模型、权限体系、应用运行时和插件机制。
- **Software Engineering Researcher**：负责一手资料研究、架构对比、技术实验、客观验证和可复现结论。
- **Software Quality & Security Architect**：负责测试架构、自动化验证、代码质量、隔离安全、发布治理和工程评估。

上述身份代表分析视角，不要求创建对应数量的 AI Agent。应采用最小必要角色和协作机制，避免过度设计。

### 1.1 最高研究原则

1. **深度优先**：深入研究决定项目成败的核心问题，不以研究平台数量、功能数量或文档篇幅作为成果。
2. **第一性原理**：从软件开发活动、业务需求表达、平台能力抽象和可执行模型出发，重新推导架构，而不是照搬现有低代码产品。
3. **证据优先**：优先使用源代码、官方技术规范、架构实现、运行实验和自动化测试，不依赖二手技术文章得出重大结论。
4. **假设可证伪**：重要架构假设必须有验证方法、失败条件和替代方案。
5. **工程闭环**：所有核心技术能力最终都要通过真实运行的系统证明，不能只停留在架构图和设计文档。
6. **最小必要复杂度**：能用简单可靠架构解决的问题，不引入复杂分布式系统、多 Agent 或额外抽象。
7. **面向长期演进**：优先解决平台底层模型、扩展边界与兼容性问题，避免为短期演示牺牲长期架构。
8. **客观评价**：通过可复现测试、量化指标、独立验收和对照实验判断成果。
9. **明确不确定性**：区分已验证事实、合理推断、架构假设、设计建议和待验证事项，不得将推测写成事实。
10. **允许否定原始设想**：如果实验证明某项设计成本过高、可靠性不足或技术路线不成立，必须提出修改、降级甚至放弃的建议。

## 二、项目背景与核心目标

### 2.1 项目名称

**OpenAILCAP（Open AI-Native Low-Code Application Platform）**

项目目标是从零构建一套 AI 原生、可扩展、支持多应用的软件开发平台。

OpenAILCAP 不应是简单地在传统低代码平台中增加 AI 助手，也不是在 AI 编码工具外部包装一个可视化界面。

其核心定位是：

**以 AI 为主要软件开发执行主体，以元数据驱动低代码体系作为基础能力，以自主代码开发作为扩展能力，通过统一应用模型、工具协议、工程流水线和应用运行机制，支持从自然语言需求到可运行应用的完整开发生命周期。**

### 2.2 三种开发模式

**模式一：AI 驱动的低代码配置开发**

用户使用自然语言描述需求，AI 自动理解业务、规划功能、创建数据模型、生成页面、配置组件、建立业务流程、设置权限并完成验证。

优先使用平台已有能力，不编写不必要的自定义代码。

**模式二：AI 驱动的自定义代码开发**

当业务无法通过现有低代码能力合理实现时，AI 可以自动创建自定义组件、服务、业务逻辑或插件。

应支持从需求分析、代码生成、编译构建、测试、自动修复、集成、部署到运行验证的完整闭环。

普通开发过程尽可能不依赖人工编码，但必须受到安全权限、环境隔离和发布策略约束。

**模式三：传统人工开发**

开发人员可以完全不使用 AI，通过可视化编辑器、配置界面和开发接口独立完成应用开发。

AI 生成的配置与代码必须可由人工理解、修改和维护。

人工修改后的应用，也必须能够重新交由 AI 继续开发。

三种模式最终生成的应用，应具备一致的运行、权限、版本管理、测试和部署能力。

### 2.3 核心约束

- 原生支持 AI 开发，而不是事后外挂 AI。
- AI 开发、人工开发可以交替进行。
- 平台配置开发与自定义代码开发可以组合使用。
- 支持多应用创建、独立管理和部署。
- 支持功能组件、业务能力、数据连接器、Agent 工具和自定义插件扩展。
- 不强制所有业务都使用 AI。
- 不强制所有业务都使用低代码。
- 自动开发结果必须可检查、可修改、可回滚、可持续演进。
- AI 不可绕过平台安全策略和授权机制。
- 设计时关注企业级适用性，但初期不追求一次实现全部企业级功能。

## 三、必须优先回答的核心研究问题

在进行完整技术选型和功能设计之前，必须深入回答以下问题。

### 3.1 AI 和低代码平台如何真正融合？

重点研究：

1. AI 应直接修改低代码平台数据库，还是通过统一工具 API 操作？
2. 是否需要统一的 Application IR（应用中间表示）？
3. Application IR 与数据模型、页面 Schema、流程定义、权限规则、自定义代码如何映射？
4. 是否需要统一的 Application Manifest 管理应用依赖与版本？
5. AI 与人工如何操作同一个应用模型？
6. AI 修改配置和代码时如何进行差异分析、冲突检测与回滚？
7. 如何保证配置编辑器、代码工作区和运行时的状态一致？
8. 复杂业务应作为元数据规则、自定义函数、服务还是插件实现？
9. 如何避免平台元数据能力不断膨胀，最终形成难以维护的复杂 DSL？
10. 如果不采用统一 Application IR，是否存在更简单、可靠的替代架构？

不能默认 Application IR 一定正确，应通过至少两种候选方案进行权衡和实验。

### 3.2 AI 如何判断采用配置还是代码？

必须研究并验证：

- 平台能力发现机制。
- 组件能力与元数据 Schema 描述。
- AI 工具调用契约。
- 配置能力与代码能力的路由机制。
- 无法配置时的升级路径。
- 混合开发场景中的依赖关系。
- 如何避免 AI 为简单功能生成大量代码。
- 如何识别 AI 对平台能力的错误理解。
- 如何在失败后回退、重新规划或转换实现路径。

要求输出一个可验证的开发模式选择机制，而不只是编写一段分类 Prompt。

### 3.3 AI 自定义开发如何形成闭环？

研究完整过程：

需求输入 → 需求结构化 → 任务规划 → 代码开发 → 构建 → 自动测试 → 问题定位 → 自动修复 → 集成 → 部署 → 运行验证。

必须分析：

- Agent 如何获取当前应用和平台上下文。
- 如何发现正确的扩展点。
- 代码工作区如何创建与隔离。
- Agent 是否必须具备直接 Shell 权限。
- 如何控制代码变更范围。
- 如何限制模型循环修复和无限消耗。
- 如何管理多次开发会话与中断恢复。
- 如何进行自动测试和独立验证。
- 如何完成部署及失败回滚。
- 如何进行审计和追溯。
- 如何确保人工代码不被意外覆盖。

### 3.4 平台如何保持长期扩展性？

重点不是列举插件种类，而是确定统一扩展机制是否可行。

研究：

- 插件的生命周期与注册机制。
- 插件 Manifest、版本与依赖。
- 插件前端、后端和运行时边界。
- 插件权限与资源隔离。
- 插件对外暴露的能力契约。
- AI 如何发现、理解与调用新插件。
- 新插件接入是否需要修改核心系统。
- 插件升级如何处理兼容性。
- 插件异常是否可能影响其他应用。
- 自定义代码如何封装为可复用能力。

### 3.5 平台最小内核是什么？

必须区分：

- 不可缺少的核心内核能力。
- 可通过插件扩展的能力。
- 仅属于设计器的能力。
- 仅属于运行时的能力。
- 仅属于 AI 开发层的能力。
- 可以复用成熟开源组件的能力。

要求识别哪些能力必须自主研发，哪些可以集成成熟技术，不以“从零开发”为理由重复制造所有基础设施。

## 四、研究方法与证据标准

### 4.1 研究方法

必须综合采用以下方法：

**A. Hypothesis-Driven Research：假设驱动研究**

建立核心假设登记表，每个假设包含：

- 假设编号和内容。
- 为什么重要。
- 当前证据。
- 可证伪条件。
- 最小验证实验。
- 成功和失败标准。
- 风险与替代方案。
- 当前验证状态。

**B. First-Principles Analysis：第一性原理分析**

从业务需求、开发行为、系统模型和执行机制重新推导，不直接沿用竞争产品功能划分。

**C. Capability Mapping：能力映射**

将用户开发任务映射为平台原子能力，识别重复能力、基础能力和扩展能力。

**D. ATAM：架构权衡分析**

重点分析可扩展性、可修改性、安全性、隔离性、性能和工程复杂度之间的取舍。

**E. ADR：架构决策记录**

每项关键技术选择必须说明：

- 决策问题。
- 候选方案。
- 原始证据。
- 对比指标。
- 实验结果。
- 选择理由。
- 被否决方案。
- 已知代价。
- 重新评估的触发条件。

**F. Threat Modeling：威胁建模**

覆盖 Prompt Injection、越权工具调用、代码执行逃逸、依赖供应链风险、跨应用访问和自动部署风险。

**G. Benchmark & Controlled Experiment：基准测试与对照实验**

同一组业务需求，分别使用人工开发、现有低代码开发和 OpenAILCAP AI 开发进行验证。

### 4.2 一手资料要求

主要证据必须优先来自：

1. 官方 GitHub/GitLab 仓库及其源码。
2. 可定位的 Commit、Tag 和 Release。
3. 官方架构文档。
4. 官方 API、Schema 和插件规范。
5. 核心模块源码与调用链。
6. 官方单元测试、集成测试和 CI。
7. 数据库迁移文件及运行时实现。
8. 官方 Issues、PR 与技术讨论。
9. 实际部署及运行验证记录。

每项重大结论需要提供可追溯来源。

对于源码证据，应尽可能记录仓库地址、版本或 Commit、文件路径和关键实现位置。

不能仅凭 README 中的功能描述判定已经实现某种技术能力。

无法获得源码或运行证据的项目，必须标明证据限制。

## 五、七阶段研究与研发计划

严格按七个阶段推进。阶段之间设置验证门槛，不允许未经验证的关键假设被当作已确认事实。

### 第一阶段：开源低代码平台与 AI 开发技术深度调研

**目标：不是寻找功能最多的平台，而是寻找对 OpenAILCAP 核心架构最有价值的参考实现。**

#### 1.1 候选项目筛选

重点研究：

- NocoBase
- ToolJet
- Appsmith
- Budibase

根据研究结果补充少量具有独特架构价值的候选项目，避免无目的地扩大数量。

还应研究必要的 AI 开发工具或框架，但重点限于 Agent 工具执行、代码工作区、自动测试和开发闭环。

#### 1.2 功能研究

建立统一功能分类体系。

至少覆盖：

- 多应用及应用生命周期管理。
- 数据源和数据模型。
- 页面、布局和组件。
- 表单与数据交互。
- 业务逻辑与工作流。
- API 与外部系统集成。
- 用户、角色、组织及权限。
- 自定义代码及组件。
- 插件扩展机制。
- 调试、测试、发布与版本管理。
- AI 需求理解。
- AI 数据建模。
- AI 页面配置。
- AI 业务流程配置。
- AI 代码开发。
- AI 测试、修复、部署。
- AI 与人工协同编辑。

但功能分类只是研究索引，不是要求 OpenAILCAP 第一版本全部实现。

每项功能必须区分：

已实现、部分实现、依赖扩展、仅文档声明、未验证和不支持。

#### 1.3 技术架构研究

对最值得深入的项目，研究：

- 整体架构和源码结构。
- 核心元数据模型。
- 页面 Schema。
- 运行时与设计器关系。
- 数据模型和业务模型。
- 扩展接口。
- AI 工具调用方式。
- 配置或代码的持久化方式。
- 编辑和发布机制。
- 多应用隔离方式。
- 权限、安全与升级机制。

必须绘制关键调用链或数据流，并标明源码依据。

#### 1.4 统一业务场景复现

优先选择以下典型任务：

1. 合同信息管理、查询、登记。
2. 金额阈值驱动的多级审批。
3. 一项低代码难以表达的复杂自定义业务规则。
4. 人工修改 AI 生成成果后，AI 继续修改。
5. 创建一个插件并让 AI 调用其能力。

重点记录：

平台实际支持程度、需要的人工操作、必须编写的代码、AI 能够完成的步骤以及最终验证结果。

#### 1.5 交付成果

- 《开源低代码平台深度研究报告》
- 《低代码与AI能力对照矩阵》
- 《核心技术实现与源码证据清单》
- 《关键架构机制研究报告》
- 《OpenAILCAP可借鉴架构与应避免问题》
- 《核心技术假设及验证计划》

**阶段门禁 G1**

必须确定：

- 哪些现有机制适合借鉴。
- 哪些机制不能直接复用。
- 哪些问题需要自主架构创新。
- 最关键的技术风险。
- 下一阶段需要优先验证的技术假设。

不能以完成文档数量作为通过依据。

### 第二阶段：OpenAILCAP 平台功能体系设计

**目标：设计满足 AI 原生开发目标所需要的最小完整能力体系。**

#### 2.1 平台能力分层

建议先研究以下逻辑分层是否合理：

- 平台基础内核。
- 应用定义与元数据层。
- 低代码配置与设计层。
- 应用运行时。
- 自定义代码与扩展层。
- AI 开发与 Agent 层。
- 开发、测试、发布和治理层。

分层属于候选模型，必须经过职责分析和架构验证，不可直接作为最终架构。

#### 2.2 建立功能能力树

每项功能需要描述：

- 功能名称和编号。
- 所属模块。
- 目标用户。
- 业务价值。
- 核心操作。
- 输入输出。
- 依赖能力。
- 人工开发支持方式。
- AI 开发支持方式。
- 可扩展性要求。
- 安全约束。
- 验收条件。
- 优先级及版本归属。

#### 2.3 区分阶段范围

必须明确：

- MVP 必须实现。
- 第二阶段可扩展。
- 长期演进能力。
- 暂时不做的功能。

不得为了追求传统低代码平台功能完整，而推迟核心 AI 开发能力验证。

#### 2.4 必须设计的关键用户旅程

至少包括：

- 自然语言创建应用。
- AI 选择配置或自定义开发。
- 人工从零创建应用。
- 人工编辑 AI 生成的应用。
- AI 接手人工编辑后的应用。
- 创建自定义插件。
- AI 发现和使用插件。
- 应用测试、发布与回滚。

#### 2.5 交付成果

- 《OpenAILCAP产品定位与范围定义》
- 《平台功能架构》
- 《分层功能能力清单》
- 《AI与人工开发交互模型》
- 《MVP范围及非目标清单》
- 《核心用户旅程与验收场景》

**阶段门禁 G2**

要求每个 MVP 功能都能追溯到具体业务场景和核心假设，不允许存在没有明确验证价值的功能。

### 第三阶段：OpenAILCAP 技术架构设计与关键技术验证

**这是整个项目技术风险最高、必须投入最深研究的阶段。**

#### 3.1 架构候选方案

至少比较两种实际可落地的架构路线，而非只给出一种推荐方案。

重点讨论：

- 元数据驱动和代码驱动如何组合。
- 是否采用统一 Application IR。
- 应用定义与源码如何保存。
- 平台内核与业务应用如何隔离。
- AI Agent 如何操作平台。
- 插件如何注册和执行。
- 开发工作区如何隔离。
- 多应用如何运行和部署。
- 版本管理及回滚如何实现。

#### 3.2 核心模型设计

研究并设计必要的领域对象和契约，包括：

Application、ApplicationVersion、DataModel、Page、Component、Workflow、BusinessRule、Permission、Plugin、Extension、CodeArtifact、DevelopmentTask、Deployment 等。

不要求机械地创建所有实体。必须分析哪些属于独立实体，哪些属于属性、聚合或派生对象。

重点明确其生命周期、版本关系、引用关系和一致性机制。

#### 3.3 Agent 架构

研究：

- 单 Agent 与多 Agent 方案的实际差异。
- 规划、执行和验证职责是否需要分离。
- 工具注册和能力发现。
- 工具输入输出 Schema。
- 应用上下文管理。
- 任务状态与执行日志。
- 长任务中断恢复。
- 失败自动修复。
- 自主执行权限边界。
- 模型供应商与 Agent 框架解耦。

优先选择满足任务需要的最简单架构，不为追求多 Agent 而增加复杂度。

#### 3.4 开发与部署架构

设计：

**PoC-A：AI 元数据配置**

**PoC-B：AI 自定义代码开发**

实现配置能力不足的复杂业务规则，并自动完成代码构建、测试、部署至隔离环境和功能验证。

**PoC-C：AI 与人工双向编辑**

执行多轮 AI 修改与人工修改，验证代码和元数据没有非预期丢失，且业务行为保持正确。

**PoC-D：插件扩展与多应用隔离**

新增一个插件，使 AI 能发现和使用该插件；同时验证两个应用的权限、配置和运行隔离。

## 六、跨阶段质量保障机制

### 6.1 需求追踪

- 可执行测试。

- 对照实验。
- 可复现操作记录。

意见和推测可以保留，但必须明确标识。

### 6.4 反例与失败分析

不能只研究成功案例。

重点记录：

- 未成功的生成任务。
- Agent 误判。
- 元数据表达失败。
- AI 覆盖人工修改。
- 自动修复引入新问题。
- 插件兼容性失败。
- 部署失败或回滚失败。
- 跨应用安全问题。

失败案例必须用于改进架构和测试集。

## 八、最终成功标准

OpenAILCAP 的成功不是拥有最多的低代码组件、最复杂的 Agent 系统或最多的功能模块。

而是证明：

**一个用户能够通过自然语言提出真实业务需求，OpenAILCAP 能够理解并合理拆解需求，优先使用低代码能力完成配置，对超出配置能力的部分自主开发代码，通过自动测试与工程流水线形成可运行应用。应用在交付后仍能接受 AI 和人工交替修改，并保持正确性、可维护性、可扩展性与安全性。**

这个目标必须通过可运行系统、独立测试、对照实验和可复现数据证明。
