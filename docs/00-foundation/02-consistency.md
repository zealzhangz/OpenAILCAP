# 深挖主题：AI/人工双向编辑的一致性与 Application IR 取舍

日期：2026-11-21。状态：候选设计；模型层 A/B 已运行并完成首轮 10/10 场景，真实平台仍未验证。

## 问题与反例

Agent 在 t0 读到按钮 label=提交、background=blue；人工在 t1 将背景改成 gray；Agent 在 t2 从旧上下文把 label 改成送审并整页覆盖。最终“送审”出现，但人工样式被静默还原，这不算成功。[ToolJet MCP 同步测试](https://github.com/ToolJet/tooljet-mcp/blob/8a178ad34f6e3326b6957503ca4ed4f555d23096/tests/codeAppSync.test.ts) 描述了类似回归样例。

## 两种候选方案

**方案 A：统一 IR**。每个 DataModel/Page/Component/Workflow/Rule/CodeArtifact 都有稳定 ID、Schema 版本，所有操作采用受控 Patch。优势是集中校验、版本追溯，劣势是复杂代码和未知插件扩展字段可能导致 DSL 无限扩张。

**方案 B：分域 Schema + Application Manifest**。数据、UI、流程、权限、代码使用独立模型，Manifest 固定资源、引用、版本与哈希；AI、人工通过同一类受治理命令修改。优势是渐进扩展，劣势是跨域事务与版本协调复杂。

两者必须对同一业务样例做 A/B 验证，不能先选技术路线再倒推合理性。初始倾向是先用 B 的最小能力契约实现冲突检测，再判断统一 IR 是否带来明确优势。

## 修改契约的建议最小字段

- actor：操作者及权限；
- app_id：所属应用；
- artifact_id：稳定对象标识；
- base_revision / base_fingerprint：基线；
- operations：字段级增量操作；
- preconditions：值、引用、权限前提；
- change_id：幂等键；
- expected_effects：预期变更范围；
- verification：独立读回与测试；
- rollback_ref：回滚依据。

变更在服务端基于权威快照检查，不能仅靠客户端提交的 revision。资源内原子 CAS、跨资源事务与发布回滚需要分别验证。

## 固定用例

| ID | 输入与并发 | 预期 |
|---|---|---|
| C01 | 人工改样式，AI 改按钮文本 | 两项修改均保留 |
| C02 | 人工、AI 改同一文本 | 显式冲突，不静默覆盖 |
| C03 | revision 相同但内容已变化 | 指纹/强并发令牌检测变化 |
| C04 | 人工删除组件，AI 改其事件 | 拒绝悬挂引用 |
| C05 | 人工改审批阈值，AI 改布局 | 业务规则与布局均正确 |
| C06 | 插件未知字段新增 | 未知字段保留或明确拒绝 |
| C07 | 多资源变更中途失败 | 原子执行或经验证的补偿回滚 |
| C08 | 重复发送同一变更 | 幂等，不生成重复组件 |
| C09 | AI 改元数据、人工代码未改变 | 源码哈希保持 |
| C10 | 关闭 LLM 后人工开发 | 可正常操作并被 AI 后续接管 |

**硬性成功条件**：零静默覆盖、零未拒绝的重叠冲突、零悬挂引用、回滚业务结果一致。测试必须分别验证持久化、编辑器读回、运行结果和审计日志，不能只检查 JSON diff。

## 反对方评审问题

如果“完整 IR”带来大量映射和迁移复杂度，但没有相对分域 Schema 的可测量改善，为什么还要采用？如果插件每增加一种类型都要修改内核 Schema，是否证明 IR 越界？AI 生成的文本级合并为什么不能当作业务正确？这些反问必须以实验回答。

## 2026-11-21 首轮实验复核

已完成 [A/B 模型模拟及 28 个单测](../../experiments/roundtrip/README.md)，详见 [实测报告](../01-research/05-roundtrip-results.md)。这证明分域 Schema + Manifest 同样能够配合增量命令正确处理当前模拟的编辑场景，**尚无证据必须构建巨大统一 IR**。首轮 C03 失败并暴露了“同 revision 内容漂移后可信版本基线的重建”缺口，增加版本采纳模拟接口后通过。应在真实编辑器与持久化环境下继续证伪。
