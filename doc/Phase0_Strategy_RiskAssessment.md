## 0.2 商业模式前置确认

### 0.2.1 三条可选路线分析

#### 方案 A：完全开源（社区驱动）
**优点：**
- 社区贡献者多，创新快
- 市场认可度高（如 WordPress 生态）
- 二次开发友好

**缺点：**
- 商业变现困难
- 企业级支持有限
- 功能方向易分散

**适合场景：** 初创团队、追求市场占有率

---

#### 方案 B：企业版订阅（Mendix/OutSystems 模式）
**优点：**
- 商业化变现直接
- 企业级支持完整
- 功能方向聚焦

**缺点：**
- 初期投入大、回本周期长
- 用户获取成本高
- 对标国际巨头难度大

**适合场景：** 大团队、充足融资、明确商业目标

---

#### 方案 C：混合生态（开源社区+企业版）
**优点：**
- 社区与商业平衡
- 开源版建立用户基础，企业版增加收入
- 风险分散

**缺点：**
- 维护复杂度高
- 社区与企业版功能分野困难

**适合场景：** 有融资、需要长期运营、追求生态

---

### 0.2.2 建议选择：混合生态（方案 C）
**理由：**
1. 开源版聚焦 MVP（表单+CRUD+权限），吸引用户
2. 企业版加入（高级 AI、多租户、SLA 保障），向上销售
3. 社区驱动插件生态，降低维护成本

**定价建议：**
```
开源版：免费（包含核心表单、CRUD、基础工作流）
企业版：
  - 中型企业 (100-500 员工): $5k/年（5 应用）
  - 大型企业 (>1000 员工): $20k/年（无限应用）
  - 专业服务包：$500/小时（咨询、定制、培训）
```

### 0.3.2 失败处理与用户修正循环

```
AI 生成 → 自动测试 → 是否通过？
                 ├─ 是 → 展示给用户审查 → 确认 → 部署
                 └─ 否 → 记录失败原因
                      ├─ 语义理解错误 → 重新理解需求
                      ├─ 代码缺陷 → 修复或拒绝
                      └─ 安全问题 → 拒绝 + 告警

用户修正流程：
用户反馈 "生成的不对" 
  → 收集用户修正意见
  → 记录为训练样本
  → 下次相似需求调用时优先使用这个修正版本
  → 定期反馈改进效果给用户
```

## 0.4 技术风险前置规避

### 0.4.1 AI 幻觉处理机制

#### 风险 1：AI 反复改坏代码
**症状：** 用户 A1 版本，AI 修改成 A2 版本，用户再改 A3，AI 又改成 A4...

**防护方案：**
```
1. 版本隔离策略
   - 每个用户修改创建新分支（git flow）
   - AI 生成也创建分支，不直接修改主分支
   - 用户决策合并时机与规则

2. 修改提示词约束
   - 明确告诉 AI："只修改 XXX 部分，其他保持不变"
   - 提供上下文："当前代码版本号 v3，用户修改位置是..."

3. 人工审查关卡
   - P0 功能（权限、支付）必须人工审查
   - P1 功能建议人工审查
   - P2 功能允许自动部署（但留可回滚）

4. 自动回滚策略
   - 部署后若错误率 >5% 自动回滚到上个稳定版本
   - 通知用户："发现问题已回滚，请重试"
```

#### 风险 2：用户需求理解错误
**症状：** 用户说"给我做个订单系统"，AI 生成的不是用户想要的

**防护方案：**
```
1. 澄清式对话
   AI 收到需求后，自动提出 5-10 个澄清问题：
   - "订单包含哪些字段？"
   - "需要多少个审批环节？"
   - "预期多少用户并发？"
   用户回答后再生成

2. 生成前展示计划
   - 生成前展示 BPMN 草图
   - 展示预计的数据模型
   - 让用户确认再开始生成

3. 增量生成 vs 一次性生成
   - 表单先生成基础字段，用户确认
   - 再生成列表视图，用户确认
   - 再生成工作流...
   （降低一次性理解错误的风险）
```

### 0.4.2 多租户隔离与沙箱

#### 核心需求
```
1. 代码执行隔离
   - 用户 A 的代码不能访问用户 B 的数据
   - 用户代码执行超时不能影响系统

2. 资源限制
   - 单个应用占用 CPU ≤ 20%
   - 单个应用内存 ≤ 512MB
   - API 调用频率 ≤ 1000/min

3. 权限隔离
   - 应用级：谁能创建、编辑、删除应用
   - 数据级：哪些数据在哪些应用可见
   - 代码级：谁能审查、部署代码
```

#### 实现方案
```
1. Docker 沙箱
   每个应用/每个用户的代码在独立容器运行
   - 自动清理资源
   - 超时自动 kill

2. 权限模型（RBAC + ABAC）
   - 角色定义（Admin、Manager、Developer、Viewer）
   - 属性判断（部门、应用、数据来源）

3. 审计日志（不可篡改）
   - PostgreSQL WAL（Write-Ahead Log）
   - Elasticsearch 存储审计事件
   - 定期校验日志完整性
```
