#### 数据模型

```typescript
// 部门模型
interface Department {
  id: string;
  code: string;              // 部门代码，如 DEPT001
  name: string;
  parentId?: string;         // 上级部门 ID
  level: number;             // 层级深度（0=顶级）
  manager: string;           // 部门负责人 ID
  costCenter?: string;       // 成本中心代码
  createdAt: Date;
  updatedAt: Date;
}

// 岗位模型
interface Position {
  id: string;
  code: string;              // 岗位代码，如 POS001
  name: string;              // "销售主管"
  level: number;             // 职级: M1/M2/M3...
  
  // 权限模板关联
  permissionTemplateId: string;
  
  // 工作流权限
  workflowPermissions: {
    flowId: string;
    allowedActions: string[]; // ["approve", "reject", "delegate"]
  }[];
  
  createdAt: Date;
}

// 人员模型
interface Employee {
  id: string;
  code: string;              // 工号
  name: string;
  department: {
    id: string;
    name: string;
  };
  position: {
    id: string;
    name: string;
    level: string;
  };
  manager?: string;          // 直接主管 ID
  
  // 权限继承
  inheritedPermissions: Permission[];
  extraPermissions: Permission[]; // 额外权限
  
  createdAt: Date;
}

// 权限推荐引擎输入
interface PermissionRecommendationContext {
  employeeId: string;
  department: Department;
  position: Position;
  
  // 历史操作
  recentActions: ActionLog[];
  
  // 同岗位其他人的权限
  peerPermissions: Permission[];
}
```

#### AI 权限推荐算法

```
当编辑人员信息时：
  1. 提取岗位模板权限 (基础)
  2. 分析同岗位/同部门其他人的权限配置
  3. 结合历史操作日志 (该人员过去一个月访问过什么？)
  4. 对比行业通用权限模型
  
  输出建议 (按置信度排序):
  - "销售主管通常需要 [订单审核权] 95% 置信"
  - "你部门的其他主管都有 [月度报表权] 90% 置信"
  - "基于你的操作历史，建议添加 [客户导出权] 82% 置信"
```

#### 国密算法集成方案

**问题：** 国标 6.6.2.2 明确要求"采用国家密码管理机构规定的密码算法"，不能仅用 TLS 1.3 + AES-256。

**解决方案：**

```
技术栈补充:
├─ GmSSL / TongSuo (开源国密 SSL 库)
├─ SM2: 公钥密码算法 (椭圆曲线)
├─ SM3: 密码哈希算法 (256 位)
├─ SM4: 对称密码算法 (分组密码)
└─ 国密证书支持

应用层：
1. 通信层加密 (SM2 + SM4)
   - 客户端 ←→ 服务器: 用 SM2 交换会话密钥，然后 SM4 加密数据

2. 存储层加密 (SM4)
   - 敏感数据字段 (身份证号、银行卡号等) 用 SM4 加密存储

3. 数据完整性验证 (SM3)
   - 重要操作记录用 SM3 生成摘要，防篡改

4. 数字签名 (SM2)
   - 合同、审批单据用 SM2 签名，法律效力
```

## 2026-11-28 设计一致性约束（对本文历史内容具有优先级）

本文早期模块说明、技术示例和“生产就绪规划”措辞不能覆盖当前统一架构基线。实施时执行以下规则：

- AppSpec 是跨设计器、Agent、编译器和运行时的唯一应用定义；模块本地对象仅作为编辑缓冲区，提交时必须转换为 AppSpec 命令并通过版本校验。
- 所有模块设计必须引用统一 API 契约、领域实体、权限策略、审计事件及测试场景；接口尚未实现时标注“目标契约”，不得伪造可调用 API。
- 租户策略统一采用 SaaS `tenant_id + RLS`，私有化独立数据库作为部署模式；不允许 schema-per-tenant、动态租户表与共享表过滤混杂。
- LogicFlow 只负责短时确定性 DAG；BPMN 负责长周期业务流程；Temporal 负责 Agent/后台长任务；BullMQ 负责短时异步任务。
- 国密/KMS、插件沙箱、设备接入、应用市场、跨语言/跨平台等设计能力，必须有实现、测试和审计证据后才能计为交付。
- 原型工作区与代码路由、模块脚本、状态字段映射见 `doc/整改/2026-11-28_设计-原型一致性契约.md`。该映射是设计和原型变更的共同验收基线。
