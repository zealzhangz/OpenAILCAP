# OpenAILCAP L3（引领级）全量交付实施基线

> 状态：整改基线已建立；**不是符合性结论**。所有条款必须以实现、测试和可复核证据关闭。
> 标准：GB/T 46900—2025《系统与软件工程 低代码开发平台通用技术要求》
> 项目目标：按第 7 章达到**引领级**，即九个能力域的全部 L1、L2、L3 阶段能力要求；不把“有页面/有设计说明”记作已交付。

## 1. 术语与目标边界

标准第 5.2 条将 L1/L2/L3 定义为初阶/中阶/高阶能力阶段；第 5.3 条的平台等级为基础级/进阶级/引领级。项目所说“按 L3 交付”在本基线中统一解释为：**以引领级为目标，满足九个能力域全部适用的 L1、L2、L3 要求**，而不是只实现标准中标注为 L3 的少数条款。

引领级的目标边界：
- 9 个能力域：应用管理、可视化开发、可视化配置、可视化支撑、资源调用、安全管理、运维管理、生态扩展、智能辅助。
- 39 个能力子域：逐一建立条款映射，不能只覆盖有原型页面的模块。
- 每个能力项必须关联：标准条款、产品功能、详细设计、前端页面/交互、后端服务/API、数据模型、权限/审计、自动化测试、证据位置和责任状态。
- 平台产品能力、应用运行能力、部署运维能力、生态开发者能力分别验收，不能用单一演示流程替代。

## 2. GB/T 46900—2025 的 L3 高阶能力项

按仓库标准文本整理，当前可明确识别的 L3 能力要求至少包括以下条款；详细设计和测试应逐项展开，并与对应 L1/L2 前置能力一并交付。

| 标准条款 | 能力项 | 必须交付的产品能力 | 可验收证据 |
|---|---|---|---|
| 6.4.2.4 | 平台级定制扩展 | 可创建/注册全新组件与服务；支持微服务、云原生等平台架构扩展；扩展包版本、依赖、权限、生命周期和兼容性管理 | SDK 示例、扩展包构建/安装/升级/卸载测试、服务注册发现、隔离和兼容性报告 |
| 6.5.3.4 | 接入设备管理 | 设备接入登记、身份认证、台账、状态监控、远程管理、告警和生命周期管理 | 设备模拟器/真实设备接入、设备证书、离线/重连、远程指令授权与审计测试 |
| 6.8.2.4.1 | 国际化开发与运行 | 平台可扩展语言包；应用交互和应用数据多语言；本地化规则；多时区处理 | 新语言包插件、跨语言应用运行、数据 locale、时区/夏令时/日期数字货币格式测试 |
| 6.8.2.4.2 | 应用提供 | 应用目录展示名称、描述、功能、截图、版本、文档；检索过滤；下载/安装；评价评论 | 应用市场完整发布、检索、安装/升级、评价审核与权限测试 |
| 6.8.3.4 | 跨平台开发 | 多开发语言兼容；多开发平台兼容 | 至少两种开发语言和两种开发/运行平台的构建、调试、打包、部署兼容矩阵 |
| 6.8.4.4 | 平台和框架扩展 | 提供开放 SDK/源代码进行二次开发；扩展点、接口契约、版本兼容和开发者文档 | SDK 可运行样例、二开插件、API/ABI 兼容测试、开发者文档与 CI 样例 |

注：L3 能力项数量不能替代引领级全量验收。第 7 章要求引领级满足九个能力域全部 L1/L2/L3 阶段能力要求。对没有 L3 子项的能力域/子域，仍必须满足该域/子域规定的全部 L1/L2 要求。

## 3. 交付证据状态（禁止混用）

| 状态 | 含义 | 能否计入交付完成 |
|---|---|---|
| S0 未分析 | 尚未完成条款拆解 | 否 |
| S1 已设计 | 有详细设计、接口和验收条件 | 否 |
| S2 原型可交互 | 前端能演示交互，可能使用模拟数据 | 否 |
| S3 已实现 | 前后端/数据/权限/审计实现可运行 | 尚不能单独判定 |
| S4 自动化验证通过 | 单元、集成、E2E、安全或兼容测试通过 | 是，需满足适用证据类型 |
| S5 独立复核通过 | 证据复核、缺陷关闭、可复现构建通过 | 是，作为最终交付状态 |

**100% 交付定义：** 适用条款全部达到 S5；条款被判定不适用时必须记录理由、审批人和影响分析，不得直接删除。S1/S2 不计入实现率；“设计覆盖率 100%”不得写成“国标符合率 100%”。

## 4. 九大能力域和三十九个子域的覆盖规则

以标准第 6 章目录为唯一分类源，逐条展开能力项，不在此人为改写或缩减标准术语。每个子域至少应包含以下设计字段：

- 目标与边界、参与角色、前置条件、主流程/异常流程；
- UI 页面、组件、交互状态、无障碍与响应式行为；
- 领域实体、字段约束、租户范围、数据生命周期；
- API 契约（路径、方法、鉴权、请求/响应 Schema、错误码、幂等）；
- 事件、任务、状态机、重试、补偿、并发与一致性；
- RBAC/ABAC 策略、数据/字段级授权、审计事件；
- 性能容量、可观测性、备份恢复、运维和安全要求；
- 测试用例 ID、测试数据、预期结果、证据链接。

九个能力域统一分解：
1. 6.1 应用管理能力域；
2. 6.2 可视化开发能力域；
3. 6.3 可视化配置能力域；
4. 6.4 可视化支撑能力域；
5. 6.5 资源调用能力域；
6. 6.6 安全管理能力域；
7. 6.7 运维管理能力域；
8. 6.8 生态扩展能力域；
9. 6.9 智能辅助能力域。

## 5. 全量功能保留基线

原型现有 14 个业务模块、18 个页面及其全部子功能作为**最低保留基线**。重构可以调整导航分组、布局、组件和交互，但不得删除能力、减少字段类型、移除操作入口或把已声明功能降级成静态展示。

|---|---|

### 5.2 现有页面与入口保留

至少保留并验收以下 18 个页面/工作区：工作台、应用管理、组织架构、数据建模、表单设计、逻辑编排、BPM 流程、任务待办、流程实例、报表设计、数据大屏、基础配置、权限管理、数据管理、代码开发、安全合规、运维部署、消息中心。

AI 入口也全部保留：AI 应用生成、AI 权限推荐、AI 数据建模、AI 字段推荐、AI 逻辑/流程生成与优化、AI 代码生成/审查、AI 报表建议、AI 部署风险分析、全局 AI 助手、跨资源搜索。AI 功能必须逐步由规则模拟替换为受控 Agent 工具链，不能删除入口来降低工作量。

### 5.3 不允许的“完成”方式

- 仅显示 Toast、静态 KPI、随机数、固定生成结果或伪造成功状态；
- 操作后不写入统一应用状态/后端，不支持刷新恢复；
- 只实现前端，没有接口契约、权限和审计；
- 页面存在但主操作不可用；
- 使用 localStorage 作为生产持久化或多用户协作方案；
- 把安全/国密/设备/插件/跨平台能力的说明卡片计作实现；
- 通过删减现有页面、字段、按钮、节点类型或导入导出功能使测试通过。

## 6. 统一应用元模型（AppSpec）约束

AppSpec 是设计器、Agent、编译器和运行时共享的唯一事实源。至少包括：
- meta：appId、名称、描述、版本、owner、tenant、locale；
- dataModels：实体、字段、关系、索引、约束、枚举、数据权限；
- ui：页面、路由、组件树、布局、主题、响应式断点；
- forms：字段、校验、默认值、事件、数据源、权限和多语言；
- logic：节点、边、变量、条件、异常、执行策略；
- workflows：BPMN 定义、任务、参与者规则、网关、事件、补偿；
- security：角色、资源、操作、RBAC/ABAC、行列策略；
- integrations：API、连接器、设备、插件和凭据引用；
- i18n：平台语言、应用语言、locale、时区；
- deployment：环境、制品、依赖、迁移、资源限制和策略；
- extensions：SDK、组件/服务扩展、插件清单和兼容范围。

所有模块只能通过版本化命令/事务修改 AppSpec；生成 SQL、Prisma、页面代码、BPMN、权限策略和制品必须可重复构建。定义 schemaVersion、迁移、引用完整性、diff、回滚、冲突解决和审计。

## 7. 功能交付的质量门

| Gate | 退出条件 |
|---|---|
| G0 基线冻结 | 全量功能目录、标准条款目录、页面清单、API/实体清单均有版本和 owner |
| G1 详细设计 | 14 模块按统一模板完成；所有能力项映射到 AppSpec、接口、数据、权限、页面和测试 |
| G2 核心技术验证 | AppSpec、生成器、租户隔离、国密、Agent、BPMN/LogicFlow、插件沙箱、设备接入有可复现 POC |
| G3 全功能实现 | 所有功能达到 S3；核心操作无静态占位；多用户持久化与审计闭环 |
| G4 自动化验证 | 全量条款的测试用例达到 S4；回归、安全、性能、兼容、恢复测试通过 |
| G5 引领级复核 | 全部适用条款 S5；差异和不适用项审批完毕；交付包/部署/运维/开发者资料齐全 |

## 8. 交付指标

- 功能保留率：100%（原功能清单逐项对照，不允许删除）。
- 标准条款设计追踪率：100%。
- 适用条款实现率：100%（达到 S3）。
- 适用条款自动化验证率：100%（达到 S4；允许有理由的人工/第三方证据补充，但不能无证据）。
- 最终复核通过率：100%（S5）。
- 核心业务 E2E：AI 需求到发布、数据模型到 CRUD、表单到运行、LogicFlow 到执行、BPMN 到审批、权限拒绝、插件安装/升级/卸载、跨语言/时区、设备接入/管理、制品部署/回滚。
- 所有指标附分母、统计规则、版本、环境、时间和原始报告。

## 9. 本轮整改执行顺序

1. 冻结标准条款和功能清单，撤销 README/覆盖矩阵中的无证据“100% 合规”宣称。
2. 冻结 ADR 和 AppSpec/IR，统一租户、技术栈、流程引擎、代码沙箱与制品模型。
3. 补齐 14 模块详细设计、API、数据、权限、状态机、异常和测试。
4. 按统一视觉系统重做全部 18 个页面和全部设计器工作区。
5. 逐模块实现真实数据流、持久化、跨模块引用和错误路径。
6. 建立全量自动化测试和标准证据库。
7. 组织独立复审；未达到 S5 的条款不得标为已交付。
