# OpenAILCAP 详细设计与原型设计评审报告

> **评审日期：** 2026-11-28  
> **仓库：** `zealzhangz/OpenAILCAP`  
> **分支：** `main`  
> **评审基线：** `57f407ee06210c07c6115c26244a9885bd5467f7`  
> **评审范围：** Phase 3 技术架构、Phase 4 详细设计/技术实现/质量与合规文档、Phase 5 原型设计及原型源码  
> **评审结论：有条件不通过，整改后复审。**

## 1. 评审结论摘要

当前仓库已形成较完整的产品功能蓝图，覆盖应用管理、组织架构、数据建模、表单、逻辑编排、BPM、权限、数据、安全和运维等模块；交互式原型具备较好的页面广度和演示价值。但现有成果主要证明“页面可以展示”，尚未证明“平台核心技术链路可运行、可验证、可安全交付”。

主要阻断点：

1. 缺少跨设计器、Agent、编译器和运行时共享的统一应用元模型（AppSpec/IR）。
2. 多租户隔离策略在 schema-per-tenant、共享表 tenant_id、动态租户表之间存在冲突。
3. 数据模型生成器存在可能生成无效或语义错误 Prisma Schema/DDL 的问题。
4. 国密示例存在固定 IV、临时密钥和完整性保护缺失等安全问题。
5. AI 能力仍以分散助手功能为主，缺少 Agent 规划、工具调用、检查点、人工审批、恢复和验证闭环。
6. Phase 5 技术 POC 的目标与当前纯前端 localStorage 演示原型不一致。
7. 国标等级分类、能力项数量及覆盖证据口径不一致。

| 评审维度 | 结论 | 主要判断 |
|---|---|---|
| 详细设计完整性 | 部分通过 | 模块覆盖较广，但跨模块统一模型、接口契约、执行语义和验收标准不足 |
| 技术架构一致性 | 不通过 | Express/NestJS、Temporal/Bull、租户隔离等多套方案并存 |
| 核心技术正确性 | 不通过 | Schema 生成、DDL 顺序、约束/关系生成和密码学方案存在问题 |
| AI 原生能力 | 不通过 | 缺少 Agent Orchestrator 和可验证的人机协同闭环 |
| 原型交互展示 | 部分通过 | 页面覆盖较好，但关键操作存在硬编码、toast 模拟和无真实数据流 |
| Phase 5 技术验证 | 不通过 | 缺少真实业务后端/API/数据库/LLM 集成及自动化测试工程 |
| 国标符合性证据 | 不通过 | 等级分类、能力项统计及设计/演示/测试证据混用 |

## 3. P0 级问题（进入 MVP 前必须整改）

### A-01 缺少统一、版本化的应用元模型（Canonical AppSpec/IR）

**评审判断：** 当前设计将 Prisma Schema、表单 JSON、BPMN XML、权限定义、资源清单等作为独立产物描述，但没有明确一个被所有设计器、Agent、编译器和运行时共同读写的权威应用定义模型。

**证据位置：** `Phase4_DetailedDesign_Enhanced.md` 的 ApplicationArtifact；`Phase3_TechnicalArchitecture.md` 的生成流程分别输出 Prisma、Express Routes、React 表单等。

**影响：** 各设计器形成多个事实来源。AI 修改数据模型后，表单字段、流程变量、权限规则、API 和部署制品可能不一致；版本回退、差异比较和跨版本迁移难以可靠完成。

**修改建议：**
- 建立版本化 AppSpec，至少覆盖应用元数据、数据模型、UI/表单、逻辑模型、BPMN/Workflow、权限、API/集成、国际化、部署配置和资源。
- 所有设计器编辑同一 AppSpec；Prisma/SQL、前端、BPMN、权限配置和运行制品由确定性编译器生成。
- 定义 schemaVersion、迁移策略、引用完整性检查、兼容性及 round-trip 规则。

**验收标准：** 提供完整订单应用 AppSpec；表单字段、BPMN 变量、权限资源引用均可校验；同一 AppSpec 可重复编译得到一致制品，并支持版本 diff/rollback。

### A-02 多租户隔离策略存在三种互相冲突的模型

**评审判断：** Phase 3 选择 PostgreSQL schema-per-tenant；Phase 4 又在共享表增加 tenant_id；同时动态业务表命名为 `tenant_{tenantId}_form_{formId}`，三种模式没有明确主从关系和安全边界。

**证据位置：** `Phase3_TechnicalArchitecture.md` §3.6；`Phase4_DetailedFunctionalDesign.md` §4.8。

**影响：** 租户上下文、外键、唯一约束、备份恢复、跨租户查询和数据迁移语义不统一。若仅依赖应用层过滤，遗漏 tenant 条件可能造成跨租户数据泄露。

**修改建议：**
- 明确唯一主方案。企业私有化/租户独立部署可采用独立数据库或 schema；SaaS 共享数据库可采用 tenant_id + PostgreSQL RLS。
- SaaS 模式下业务表统一 tenant_id，设计租户复合唯一键、租户约束外键和 RLS。
- 明确租户解析、连接池/search_path、安全上下文、缓存键、文件路径、任务队列和审计隔离规则。
- 不要混用 schema-per-tenant、共享 tenant_id 和每租户动态表命名。

**验收标准：** 两租户自动化越权测试覆盖读取、更新、删除、导出、附件、缓存、后台任务和审计查询；数据库约束或 RLS 可独立阻止越权。

### A-03 数据模型 DDL 与 Prisma Schema 生成逻辑存在正确性缺陷

**评审判断：** 技术实现文档中的 SQL 建表顺序引用尚未创建的表；SQL 与 Prisma 的 ID 类型不一致；Schema 生成器对主键、唯一约束、索引和关系生成存在错误或缺失。

**证据位置：** `Phase4_TechnicalImplementation.md` L16-L61、L91-L99、L107-L170、L513-L630。

**发现示例：**
- departments 在 employees 创建前引用 employees；positions 在 permission_templates 创建前引用该表。
- SQL 使用 UUID，而 Prisma 使用 String @default(cuid())。
- 字段已输出 @id 后又生成 @@id。
- 多个独立 unique 字段被额外组合成复合 unique。
- 索引使用 fieldId 而非字段名。
- 关系生成未完整生成外键标量字段和反向关系。

**影响：** 生成结果可能无法编译、迁移或保持业务语义，直接影响应用创建、数据完整性和版本升级。

**修改建议：**
- 统一 SQL/Prisma 的 ID 策略和数据库类型。
- 循环外键采用先建表后 ALTER TABLE 加约束，或调整建表顺序。
- 单字段主键与复合主键二选一；单字段 unique 与复合 unique 分开建模。
- 索引按字段名生成；补齐 1:1、1:N、N:M 两端定义、外键字段及 onDelete/onUpdate。
- 补齐 enum、default、precision/scale、nullable、数据库映射和字段名合法性校验。
- 生成后执行 prisma format、prisma validate，并在临时 PostgreSQL 中执行迁移。

**验收标准：** 覆盖主键、复合主键、唯一约束、复合唯一、索引、枚举、默认值、空值、循环关系及 1:1/1:N/N:M；所有 Schema 通过 Prisma validate，迁移可执行并可回滚。

### A-04 国密加密示例不具备可接受的生产安全性

**评审判断：** SM4 示例使用固定全零 IV；密钥在服务启动时随机生成且未持久化/托管；没有解密方法和密钥版本；SM3 示例只是普通哈希，不能等同于 HMAC 或可验证的防篡改链。

**证据位置：** `Phase5_Prototype_Design.md` L529-L567；原型 `security.js` L124-L132、L160-L170。

**影响：** 固定 IV 会破坏语义安全；服务重启后随机密钥变化会导致历史密文无法解密；普通哈希不能证明数据来自可信主体，攻击者修改数据后可重新计算哈希。UI 容易造成国密能力已实现的误判。

**修改建议：**
- 删除固定 IV 和进程内临时密钥方案。
- 使用经过密码评审的国密加密封装：每条密文使用唯一随机 IV/nonce，携带算法版本、keyId、IV 和完整性校验信息。
- 使用 KMS/HSM/Vault 管理主密钥和轮换；提供解密、密钥版本迁移、旧密钥保留、备份恢复和篡改检测。
- 明确 SM3、HMAC-SM3、数字签名用途，不能混称。
- 完成前，原型只能标注“安全方案演示”，不得标注“国密已启用/合规通过”。

**验收标准：** 加解密往返、服务重启后解密、密钥轮换、篡改检测、IV 唯一性、密钥权限隔离、备份恢复和性能测试通过安全评审。

### A-05 AI 原生定位尚未落实为 Agent 驱动的端到端开发架构

**评审判断：** AI 设计主要是应用生成、权限推荐、建模、代码补全、报表建议等分散能力点；没有定义 Agent 规划、工具调用、状态管理、检查点、人工审批、恢复和验证闭环。

**证据位置：** `Phase3_TechnicalArchitecture.md` §3.3；`Phase4_DetailedDesign_Enhanced.md` Part 3；原型 `app.js` 明确标注 rule-based demo。

**影响：** AI 仍是传统低代码模块中的若干助手按钮，而不是能够跨模块规划、调用工具、生成、验证、修改和交付应用的主驱动层。

**修改建议：**
- 新增 AI Orchestrator，包含需求澄清/规格、架构与数据、界面/流程/逻辑、代码、测试、安全审查、发布等 Agent。
- 通过有类型的 Tool Registry 访问平台 API。
- 定义任务状态机、计划与差异预览、权限策略、人工审批点、检查点/重试/恢复、模型路由、项目上下文、执行日志和评估机制。
- 低代码配置路径与复杂代码路径共享同一 AppSpec；用户手工编辑后 Agent 能重新读取变更。

**验收标准：** 使用真实模型服务完成“自然语言需求→澄清→计划→AppSpec→模型/表单/逻辑/BPM→生成→测试→安全检查→用户确认→发布”端到端用例；每个工具调用有权限、输入输出 schema、审计记录和可撤销变更。

### A-06 Phase 5 技术原型交付与当前代码仓库不一致

**评审判断：** Phase 5 设计要求 React SPA、NestJS、Prisma/PostgreSQL、API、国密 POC、Schema 生成和自动化测试；当前原型是原生 HTML/CSS/JavaScript 静态 SPA，状态保存在浏览器 localStorage，没有业务 API、数据库、真实 LLM 集成或测试工程。

**证据位置：** `Phase5_Prototype_Design.md` L42-L59、L65-L160、L697-L814；`openailcap-prototype/server.js`；`store.js`；`package.json`。

**影响：** 当前交付可用于产品演示和交互评审，但不能证明 Phase 5 所要求的技术可行性，也不能作为后续团队可直接依赖的后端/生成/安全实现基线。

**修改建议：**
- 将当前版本明确命名为“交互式 UI 演示原型”，不把它当作 Phase 5 技术 POC 验收。
- 单独建立技术 POC：真实 NestJS API、PostgreSQL/Prisma、真实模型服务、可运行订单应用、可执行迁移、逻辑/BPM 执行、沙箱构建与测试、CI 自动化测试。
- 若决定继续采用原生 JS，也必须同步修改 Phase 5 技术方案和验收标准。

**验收标准：** Phase 5 成功标准逐项有可复现证据，包括订单应用生成、CRUD、权限验证、真实模型调用、Schema 迁移、国密加解密、单测、E2E 和性能基准。

## 4. P1 级问题（进入 MVP Beta 前必须整改）

### A-07 技术栈选型没有形成唯一基线

**问题：** Phase 3 同时出现 Express 与可选 NestJS、Temporal 与 Bull；Phase 4/5 又将 NestJS 作为后端主框架。流程引擎、异步任务队列、BPMN 执行引擎和通用逻辑执行器职责没有最终确认。

**证据：** `Phase3_TechnicalArchitecture.md` §3.1；`Phase4_TechStack_Deployment.md` §1；`Phase5_Prototype_Design.md` §2。

**建议：** 发布 ADR，明确唯一主后端框架；明确 Bull/BullMQ、Temporal、BPMN 引擎各自职责。Temporal 不能被默认视为可直接替代 BPMN 语义的拖拽式 BPMN 引擎。同步更新架构图、部署拓扑、依赖、API 文档和 WBS。

**验收：** 全部架构与工程文档使用同一组件基线，不存在未决的主干组件“或/可选”表述。

### A-08 逻辑编排与 BPM 流程的职责边界及执行语义不清晰

**问题：** LogicFlow 与 BPMN 分别设计，但没有明确执行边界、数据上下文、事务、异常、重试、幂等、补偿、版本切换和调用关系。

**证据：** `Phase4_DetailedDesign_Enhanced.md` 模块 5；`Phase4_DetailedFunctionalDesign.md` §4.3；Phase 3 工作流引擎章节。

**建议：** LogicFlow 用于短时、确定性、可组合业务逻辑/DAG；BPMN 用于长周期、人工参与、可挂起/恢复流程。定义 BPMN Task 调用 LogicFlow 的契约、变量映射、事务边界、outbox/event、幂等键、重试、补偿、超时、版本兼容和调试协议。

**验收：** 订单创建校验逻辑由 BPMN 审批流程调用的集成测试覆盖成功、失败、超时、重试、重复请求、版本升级和补偿。

### A-09 权限模型与代码沙箱缺少可执行的安全边界

**问题：** RBAC+ABAC 主要停留在概念和示例表达式；缺少完整策略执行、拒绝优先级、租户上下文、字段/行/API 级策略，以及开发权限与运行权限分离。沙箱只有资源指标描述，没有实际隔离机制。

**证据：** `Phase3_TechnicalArchitecture.md` §3.4/§3.7；`Phase4_DetailedDesign_Enhanced.md` 权限章节；`Phase5_Prototype_Design.md` 沙箱示例。

**建议：** 将策略表达式解析为受限 AST，禁止任意 JS eval；定义 PDP/PEP、默认拒绝、显式 deny 优先及作用域。沙箱采用非特权隔离运行时、只读根文件系统、临时工作目录、seccomp/capabilities、默认拒绝网络、出站白名单、资源配额、超时和秘密代理。

**验收：** 跨租户、水平/垂直越权、ABAC 注入、沙箱逃逸基线、网络/文件访问、密钥读取和资源耗尽测试通过。

### A-10 应用制品与发布回滚缺少可复现、可审计的生命周期定义

**问题：** Artifact 虽列出 Prisma Schema、种子数据、表单、BPMN、权限和资源，但没有完整定义制品清单、编译器版本、依赖锁定、数据库迁移兼容、签名、来源追踪、环境配置和回滚策略。

**建议：** 为 Artifact 增加 manifest：appId、appVersion、AppSpec/schemaVersion、compiler/runtime version、source commit、dependency lock、database migrations、seed data、assets、permissions、environment requirements、checksum/signature、SBOM。制品不可变；发布采用兼容性迁移策略，并定义应用和数据库结构回滚方式。

**验收：** 同一不可变制品在测试/预发环境复用；验证签名、依赖、迁移、发布、失败回滚和审计链。

### P-01 AI 应用生成向导存在确定性流程缺陷且生成结果被硬编码

**问题：** `draw()` 使用闭包变量 step，但 `aiAnswer()` 递增 `this._step`，问题序号不会推进。即使进入生成阶段，`aiRun()` 也固定创建“销售订单管理系统(AI)”，没有使用用户回答，也没有真正创建数据模型、表单、BPM 或权限。

**证据：** `openailcap-prototype/public/js/modules/app-management.js` L73-L119。

**建议：** 将 step 与 answers 放在同一状态对象中；根据用户输入生成结构化需求和可编辑计划；确认后写入 AppSpec，并依次生成模型、表单、逻辑/BPM、权限和制品；失败时保留阶段状态并允许重试。

**验收：** 4 个澄清问题逐一推进；不同回答生成不同 AppSpec；刷新后可恢复任务；生成产物可在设计器中打开和编辑。

### P-02 LogicFlow/BPM 原型没有实现真实连线、执行和 BPMN 产物

**问题：** LogicFlow 仅绘制预置 edges，没有连线创建/删除；模拟测试输出固定成功结果；代码生成返回固定订单代码；AI 生成仅 toast。BPM 导出 XML 是固定样例，扩展属性前缀 oac 未声明，流程连线不完整。任务审批只修改 task.state，没有驱动真实流程实例。

**证据：** `logic-flow.js` L59-L68、L115-L150；`bpm-designer.js` L55-L78、L147-L165；`tasks.js` L52-L76、L109-L120。

**建议：** 实现连线创建/删除/编辑、分支条件和节点端口；基于图结构执行拓扑校验和模拟；代码生成读取真实节点和边。BPMN 导入/导出使用标准模型库并做 schema/语义校验；任务审批调用流程引擎推进实例。

**验收：** 订单审批流程可从画布创建、连线、配置参与者、导出并重新导入 BPMN；审批通过/拒绝真实推进流程，实例状态和审计记录同步。

### P-03 多个模块的主要操作仍是静态演示或 toast

**问题：** 数据建模 AI 的“加入画布”只提示成功，没有写入模型集合；表单、逻辑、报表保存，部署、回滚、密钥轮换、API Key 吊销等操作存在 toast 或静态内容；报表使用 Math.random 生成数据；运维 KPI 和安全状态硬编码。

**证据：** `data-modeling.js` L134-L169；`form-designer.js`；`report-designer.js` L58-L66；`operations.js`；`security.js`；`data-management.js`。

**建议：** 为交互标注真实实现、前端模拟、静态展示、规划中；核心路径不得用成功 toast 代替业务动作。真实动作更新统一状态/后端 API，并提供失败、加载、重试和审计反馈；演示数据统一标识。

**验收：** 核心操作具备持久化、刷新恢复、跨模块同步和失败路径；静态演示项不得计入“已完成/已启用/已通过”。

### P-04 国际化设计与原型实现不一致

**问题：** 多语言设计声明平台 UI 中英文 100% 覆盖；当前 i18n.js 仅有少量 common/nav/home 字典，其他模块大量硬编码中文，切换语言不会翻译完整页面。

**证据：** `Phase4_Multilingual_Design.md` L14-L45、L974-L1011；原型 `i18n.js` L1-L45；`app.js` L65-L74。

**建议：** 按模块拆分 namespace；所有 UI 文案、校验、状态、帮助文本和动态通知进入语言包；应用字段标签/枚举/帮助文本由 AppSpec 提供 locale map；统一日期、数字、货币和时区格式。

**验收：** 自动扫描可见文案 key；zh-CN/en-US 覆盖率达到约定标准；逐页面验证语言切换，应用表单、字典、报表和错误信息均完成双语验证。

### P-05 国标覆盖率、等级分类与测试证据不能相互印证

**问题：** Phase 4 合规报告出现 130 个能力项，Phase 5 覆盖矩阵和 QA 文档使用 139 项；详细设计称基础级已达标，合规报告又判定基础级不达标。覆盖矩阵把设计说明、原型静态展示和真实测试结果混合为 100% 覆盖。仓库未见可复现的自动化测试工程。

**证据：** `Phase4_国标合规性检查报告.md` L186-L224；`Phase4_QA_RiskManagement.md`；`Phase5_覆盖矩阵_100pct.md`；`Phase5_Prototype_Design.md` L728-L814。

**建议：**
- 按标准第 7 章重新建立等级矩阵：基础级按应用管理、可视化开发、可视化配置 L1 判定；进阶级再纳入安全管理 L1 及相应能力域 L1/L2。
- 6.2.4 逻辑编排为 L1，属于基础级评估范围。
- 6.2.3.3.1 流程参与者规则定义为 L2，不应列为基础级 L1 硬性缺口。
- 6.6.2/6.6.3 安全管理 L1 纳入进阶级评估，不应直接称为基础级必选项。
- 统一 130/139 的计数规则；区分设计覆盖、原型展示、代码实现、自动化测试、第三方验证五种证据状态。

**验收：** 每个标准条款有唯一 ID、等级、适用性、设计章节、代码位置、测试用例 ID、证据链接和结论；覆盖率由测试证据汇总。

## 5. P2 级问题（完善设计与交付治理）

### A-11 “14 个模块详细设计”尚未达到逐模块可实施粒度

**问题：** Enhanced 设计标题为 14 个模块，但实际展开详细设计的模块主要是 1、2、3、5、9、13；其他模块依赖旧版功能设计或简要引用。模块间缺少统一 API 契约、状态模型、权限点、错误码和测试验收条件。

**建议：** 14 个模块采用统一模板：目标/边界、角色与权限、页面交互、领域模型、API 契约、事件、状态机、异常与补偿、审计、性能/安全要求、验收用例和依赖关系。模块清单、导航页面、服务边界和数据实体建立映射。

**验收：** 14 个模块均有可评审详细设计；关键模块接口、状态迁移和端到端场景通过架构评审。

### A-12 AI 效果与平台性能数字缺少测量口径

**问题：** 文档/原型展示权限推荐准确率 >95%、AI 代码时间下降 70%、AI 应用 5 分钟生成、API P95 268ms、可用性 99.97%、覆盖率 96% 等数字，但没有数据集、样本量、环境、基线和测量报告。

**建议：** 指标标注为目标值、演示数据或实测值；实测值附环境配置、负载模型、样本量、时间窗口、统计口径和原始报告。AI 质量按任务集、人工评分标准、成功率、返工率和安全缺陷率测量。

**验收：** 每个百分比和性能数值均可追溯到可复现报告；无证据指标改为目标或演示值。

### A-13 原型 README、依赖声明与实际服务器实现不一致

**问题：** README 声明 Express 后端和多组 /api 路由，并将 server.js 描述为 Express 服务；实际 server.js 使用 Node 内置 http 只提供静态文件。package.json 声明 express/cors/body-parser，但没有实际 API；README 称内存数据库，而 store.js 使用 localStorage。

**证据：** `openailcap-prototype/README.md`；`package.json`；`server.js`；`store.js`。

**建议：** 若保留纯前端演示定位，删除虚构 API 路由和未使用依赖，README 明确 localStorage 与静态服务器；若保留 API 文档，则实现对应后端路由、请求/响应 schema、错误码和测试。

**验收：** README、package.json、server.js、实际 API 和持久化机制完全一致；列出的 API 均有可运行测试。

## 6. GB/T 46900-2025 对标口径修订

国家标准信息平台显示 GB/T 46900-2025《系统与软件工程 低代码开发平台通用技术要求》为现行标准，发布日期 2025-12-31，实施日期 2026-07-01。标准第 5.2 条给出 9 个能力域、39 个能力子域及 L1/L2/L3 演进阶段；第 7 章规定不同平台等级的组合要求。

- **基础级：** 应用管理、可视化应用开发、可视化应用配置能力域的 L1。
- **进阶级：** 应用管理、安全管理 L1，以及可视化开发、可视化配置、可视化支撑、资源调用、运维管理的 L1/L2。
- **引领级：** 9 个能力域全部 L1/L2/L3。
- 6.2.4 逻辑编排为 L1，属于基础级评估范围。
- 6.2.3.3.1 流程参与者规则定义为 L2，不应标注为基础级 L1 硬性缺口。
- 6.6.2/6.6.3 安全管理 L1 应纳入进阶级评估，不应直接称为基础级必选项。
- “139 项”不是标准第 5.2/第 7 章直接规定的固定计数，应明确项目自己的原子能力项拆分规则；当前文档 130/139 不一致，必须先对齐。

**官方标准信息：** https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=C38D84136199A885C5D4CD3DB26E8B4F

## 7. 推荐的目标架构与设计收敛方向

| 架构层 | 建议职责 |
|---|---|
| 交互层 | AI 对话工作台 + 传统设计器；对话与设计器共享同一应用状态 |
| AI 编排层 | Agent Orchestrator、任务状态机、工具注册表、模型路由、上下文/知识、人工审批、检查点、评估和审计 |
| 统一模型层 | 版本化 AppSpec/IR，覆盖数据、表单、页面、逻辑、BPM、权限、API、插件、国际化和部署 |
| 编译与验证层 | 确定性编译器生成 SQL/Prisma、前端、BPMN、权限策略和制品；执行静态校验、类型检查、测试和安全扫描 |
| 运行时层 | 区分低代码元数据解释运行时与自定义代码运行时；BPMN 长流程和 LogicFlow 短逻辑分工明确 |
| 平台服务层 | 认证授权、租户隔离、审计、制品仓库、插件/集成、消息、调度、监控和部署 |
| 基础设施层 | 通过 ADR 固定 NestJS/数据库/队列/流程引擎/对象存储/沙箱技术；明确私有化与多租户部署配置 |

## 8. 整改顺序与阶段门

### Gate A：架构基线冻结
- 完成 ADR：技术栈、租户隔离、运行模式、BPMN 引擎、LogicFlow 引擎、队列和沙箱。
- 完成 AppSpec/IR 结构、版本兼容策略和订单应用样例。
- 完成标准等级和能力项计数口径统一。

### Gate B：核心技术 POC
- 数据模型生成器通过 Prisma validate 和 PostgreSQL 实际迁移测试。
- 国密加解密、密钥管理和完整性验证通过安全评审。
- 真实 LLM/Agent 工具调用完成订单应用生成，产物可回写设计器。

### Gate C：交互原型闭环
- AI 向导按输入推进，生成结果不是固定样例。
- LogicFlow 可连线、校验、执行和生成与画布一致的代码。
- BPMN 可导入/导出/执行；任务审批真实驱动流程实例。
- 演示项标识清楚，核心动作具备持久化、失败处理和审计。

### Gate D：工程化验收
- 补齐单元、集成、E2E、权限、安全、性能和回归测试，并接入 CI。
- 建立标准逐项追踪矩阵：条款→设计→代码→测试→证据。
- 所有 P0 关闭；P1 有明确关闭证据后，方可进入 MVP Beta。
